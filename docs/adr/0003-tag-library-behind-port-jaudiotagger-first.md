# 0003 – Tag library behind TagReader/TagWriter ports, jaudiotagger first

Status: accepted · Date: 2026-10-22 · Details: [architecture §5.2–5.3, §6.2–6.3, §9](../architecture.md)

## Context
We must read ID3v1/v1.1 and ID3v2.2/2.3/2.4 (including both at once), write user-selected versions and encodings,
preserve unknown frames, and stay able to switch to mp3agic. jaudiotagger (`net.jthink:jaudiotagger`) covers every
version and later FLAC/MP4. However, it has process-wide mutable options (`TagOptionSingleton`), chatty JUL logging,
and it needs reflection metadata for native image.

## Decision
- Two ports in core: `TagReader` (read-only, thread-safe for different files) and `TagWriter`
  (`capabilities`, `preflight`, `writeCopy(source, target, request, …)`).
- The **port shape is copy-based** (`writeCopy` into a caller-chosen temp path), never in-place. This fits the
  export-only policy (ADR 0004) and mp3agic's `save(newFile)` model.
- The domain is format-neutral: `Field` (title, artist, album artist, …), `FieldValue`, `MediaMetadata`,
  `TagLayer(version, metadata)` per slot. Frame IDs never appear in core.
- ID3-specific *user* concepts are core types, as CLAUDE.md requires: `TagWriteOptions`, `TagVersion`, the ID3v1
  genre table, and `Id3v1Projection`. Core computes the ID3v1 bytes (transliteration/truncation) so that dry-run
  and the written result agree for every adapter.
- Adapters declare `FormatCapabilities` (writable versions, encodings, fields, cover). Core validates options against
  them before writing.
- First implementation: `music-studio-tag-jaudiotagger`. `TagOptionSingleton` is touched only there, under a lock
  held for the whole write. JUL logging is lowered to WARNING in the adapter. Native metadata comes from the tracing
  agent and is committed.

## Alternatives
- *mp3agic first*: smaller and simpler, but it cannot write ID3v2.2 and has no FLAC/MP4 path.
- *Own ID3 implementation*: full control, but a large amount of format work and risk. Not justified now.
- *Expose a generic frame map through the port*: maximum fidelity, but it leaks the ID3 model and breaks
  format neutrality.

## Consequences
- Switching to mp3agic = new adapter + `TagReaderContract`/`TagWriterContract` + one line in `app`. Its capabilities
  grey out v2.2.
- jaudiotagger writes are serialised (fine, since export is sequential).
- Verification after writing re-reads with the *same* adapter. Independence comes from the contract fixtures, which
  are generated by other tools.
